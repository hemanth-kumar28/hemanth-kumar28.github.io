1Effort Estimation Techniques

Predicting effort, cost, staffing and duration before development is complete

Effort estimation

Effort estimation predicts the work needed to develop a project, usually in person-hours, person-days or person-months. It gives the basis for schedules, cost estimates, resource allocation, bids, risk planning and progress control.

Estimates depend on project size and complexity, requirement stability, team capability, technology, development method, reuse, customer involvement, risk, and tool support. An estimate is a reasoned prediction with stated assumptions, not a guarantee.

Common estimation approaches
MethodUse it whenStrengthMain limitation
Expert judgmentRequirements are incomplete, work is novel, or history is limited.Uses relevant technical and domain experience.Subject to optimism, anchoring and hidden assumptions.
Estimation by analogyReliable data exists for a genuinely similar completed project.Anchors the estimate in observed effort.False similarity produces misleading estimates.
Top-downAn early, system-level estimate is needed before tasks are stable.Fast and includes integration effort.Can overlook detailed work.
Bottom-upA detailed work breakdown and stable requirements exist.Traceable to individual tasks.Time-consuming and weak when the scope is still changing.

Expert judgment

Use people with relevant experience, define the scope and assumptions first, collect independent estimates, reconcile differences, record a range and rationale, and compare the result with actual performance later. A Delphi-style review reduces authority bias by allowing independent rounds before a moderated discussion.

Estimation by analogy

Select a completed reference project with trustworthy actual data. Compare size, technology, interfaces, team capability, reuse, quality target and schedule pressure. Scale for size, then state explicit adjustments for the differences.

Estimatenew = Estimatereference × (Sizenew / Sizereference) × adjustment factors
Use a range if key differences remain uncertain.

2Function Point Methods

Sizing business functionality independently of the programming language

Albrecht Function Point Analysis

Albrecht’s Function Point Analysis (FPA) measures the functionality delivered to users. It is used for software sizing, effort and cost estimation, productivity comparison, project planning and scheduling.

Albrecht function types and complexity weights
Function typeMeaningLowAverageHigh
EI — External InputData or control information entering the application.346
EO — External OutputProcessed information leaving the application, often with derived data.457
EQ — External InquiryAn input-output retrieval with no significant derived processing or update.346
ILF — Internal Logical FileLogical data maintained within the application boundary.71015
EIF — External Interface FileLogical data referenced by the application but maintained outside its boundary.5710
UFP = Σ (count of a function type × its complexity weight)

Value Adjustment Factor

Rate each General System Characteristic (GSC) from 0 to 5: no influence, incidental, moderate, average, significant, or strong. The 14 GSCs are data communications, distributed processing, performance, heavily used configuration, transaction rate, online data entry, end-user efficiency, online update, complex processing, reusability, installation ease, operational ease, multiple sites and facilitate change.

DI = Σ 14 GSC ratings   (0 ≤ DI ≤ 70)
VAF = 0.65 + 0.01 × DI   (0.65 ≤ VAF ≤ 1.35)
Adjusted FP = UFP × VAF

Function Point Mark II

Mark II measures logical transactions through input data element types (Ni), entity-type references used during processing (Ne), and output data element types (No). It does not use Albrecht’s EI/EO/EQ/ILF/EIF weight table or its VAF.

Mark II FPI = 0.58 ΣNi + 1.66 ΣNe + 0.26 ΣNo
Important distinction

Do not mix the two methods. Albrecht counts five function types and applies their weights; Mark II counts transaction inputs, entity references and outputs.

3COCOMO and Object Points

Algorithmic cost estimation and the COCOMO II Application Composition model

Constructive Cost Model (COCOMO)

COCOMO is Barry Boehm’s software cost-estimation model. Classic COCOMO converts estimated size in KLOC into effort and development time. Basic COCOMO uses size and development mode; Intermediate COCOMO adds effort-adjustment factors; Detailed COCOMO distributes the estimate by lifecycle phase.

Detailed COCOMO distributes the estimate across lifecycle phases; coefficients vary by mode.

4Module 4 — Project Planning and Risk Management

Integrating uncertainty into scope, schedule, cost, quality and stakeholder decisions

Project planning

Identify stakeholders→Set priorities→Define deliverables→Build schedule→Assess risks→Approve baseline

The approved scope, schedule and cost plan becomes the baseline for monitoring and change control; the risk plan and register stay connected to it and are reviewed as conditions change. Risk management belongs within project planning: uncertain requirements affect scope; uncertain activities affect schedule and critical-path buffers; resource or supplier uncertainty affects cost and procurement plans.

Nature and types of risk

A risk is an uncertain future event or condition that may affect a project objective, positively or negatively; the response strategies below focus on threats. A hazard is a source or condition that can cause harm. An issue is a risk that has already occurred.

Risk categories used in software projects
TypeExamplesTypical impact
TechnicalUnproven technology, integration failure, performance shortfallRework, quality failure, delay
ProjectPoor estimates, scope drift, resource shortage, unrealistic scheduleOverrun or missed milestones
People / organisationalKey-person loss, skill gap, slow decisions, conflictReduced productivity or knowledge loss
Business / externalBudget cut, supplier failure, regulatory change, contract disputeCost increase, redesign or cancellation
Security / operationalAttack, data loss, outage, weak backup or recoveryService disruption, compliance or reputational loss

Hazard identification and assessment

Identify hazards with historical checklists, lessons learned, brainstorming, stakeholder interviews, work-breakdown-structure review, architecture and interface reviews, and supplier assessment. Then analyse probability and impact, rank exposure, and decide which hazards need active treatment.

Risk Exposure = Probability of occurrence × Impact (severity)
Assessment condition

Probability and impact must use compatible scales. Rank risks consistently, then set an explicit threshold for active response rather than treating every recorded risk equally.

Example hazard assessment: banking system

Risk control continuously monitors indicators, checks mitigation effectiveness, executes contingency plans and communicates material changes.

5PERT and Critical Path Analysis

Planning and controlling projects when activity durations are uncertain

PERT (Program Evaluation and Review Technique) uses three time estimates and a network of dependencies to estimate duration, identify critical activities and reason about completion uncertainty. The critical path is the longest-duration path through the network; delaying a critical activity delays the project unless the path changes.

Three-point estimates
SymbolMeaning
toOptimistic time under favourable conditions.
tmMost likely time under normal conditions.
tpPessimistic time under unfavourable conditions.
Expected duration: te = (to + 4tm + tp) / 6
Activity variance: σ² = ((tp − to) / 6)²
Activity standard deviation: σ = (tp − to) / 6
  1. List activities and dependenciesBreak down the project and show predecessor relationships.
  2. Estimate durationsAssign to, tm and tp, then calculate te and variance.
  3. Run the networkUse a forward pass for earliest start/finish and a backward pass for latest start/finish.
  4. Find floats and the critical pathTotal float = LS − ES = LF − EF. A zero-float activity is critical under the current network.
  5. Estimate project uncertaintySum expected times and variances only along the critical path, assuming activity durations are independent.
TE = Σ te on the critical path
σ²project = Σ σ²i on the critical path
σproject = √σ²project
Z = (target date − TE) / σproject
Use Z with the supplied normal-distribution probability. Recalculate the network if an activity duration or dependency changes.

6Module 5 — Monitoring, Control and Change Management

Measure actual performance against the approved baseline and take controlled corrective action

Creating the monitoring framework

Define the approved scope, schedule and cost baselines; metrics; data sources; collection frequency; reporting format; thresholds; owners; escalation route; and review cadence.

Collecting the data

Collect trustworthy actuals on completed work, effort, cost, defects, milestones, resource use, risks and change requests from work records, timesheets, finance systems, issue/defect trackers, milestone sign-offs, risk logs and approved change records. Give each measure a clear definition, status date, owner and consistent source.

Visualizing progress

Choose a visual that answers the management question: milestone or Gantt views for timing and dependencies; trend charts for change over time; dashboards for threshold exceptions; and variance or burn-down charts for remaining work. A chart should make deviations and causes easier to spot, not decorate incomplete data.

Cost monitoring

Compare the approved cost baseline with actual cost, committed cost and the forecast needed to finish remaining work. Investigate variances early and interpret spending against completed work.

Earned Value Management

EVM combines scope, schedule and cost by comparing planned budgeted work, completed budgeted work and actual cost at the status date.

EVM measures
MeasureMeaning
PV — Planned ValueBudgeted cost of work scheduled by the status date.
EV — Earned ValueBudgeted value of work actually completed; it is not money spent.
AC — Actual CostActual cost of the completed work.
BAC — Budget at CompletionTotal approved budget for the project.
CV = EV − AC   negative = over budget
SV = EV − PV   negative = behind schedule
CPI = EV / AC   below 1 = poor cost efficiency
SPI = EV / PV   below 1 = slow progress
EAC = BAC / CPI when current cost efficiency is expected to continue
ETC = EAC − AC; VAC = BAC − EAC

Prioritising monitoring

Give priority to critical-path work, high-risk items, large cost or schedule variances, resource bottlenecks, quality defects, milestones and scope changes. Consider criticality, risk severity, cost/schedule impact, dependencies and visibility.

Getting the project back to target

When performance deviates, identify the deviation, find the root cause, assess project-wide impact, select and approve corrective action, implement it, and monitor recovery.

Plan→Monitor→Compare→Find deviation→Correct→Re-monitor

Change control

Change control is the formal process for changes to scope, requirements, schedule, cost, resources, architecture or deliverables. A change request is logged, impact is analysed, the request is reviewed and approved or rejected, the baseline is updated after approval, then the change is implemented, verified and monitored. Rebaselining without approval hides performance and breaks traceability.

7Module 5 — Contract Management and Acceptance

Managing the client–supplier agreement from requirements through formal closeout

A contract is a legally binding agreement that defines obligations, deliverables, timelines, price and terms. Contract management plans, negotiates, administers, monitors and closes the agreement while controlling changes and resolving disputes.

Purpose and participants: clarify client and supplier responsibilities, quality and delivery expectations, payment and remedies, and maintain auditable records. The customer, supplier, project manager, and legal or procurement team contribute according to their authority.

Common contract types
TypeBest fitRisk allocation
Fixed-priceClear, stable scope and measurable deliverables.More cost risk sits with the supplier.
Cost-reimbursementUncertain scope or research work requiring flexibility.More cost risk sits with the buyer.
Time and materialsWork is needed but effort and scope cannot yet be fixed.Shared through agreed rates and controls.
Unit-priceWork can be measured in standard units.Depends on quantity uncertainty and rate agreement.

Stages in contract placement

Define requirements→Prepare documents→Invite tender (RFP / RFQ)→Receive proposals→Evaluate→Negotiate→Award→Sign→Administer→Close

Requirements and acceptance needs inform the statement of work and bid criteria. Proposal evaluation compares technical capability, price, feasibility, experience and risk. Negotiation finalises scope, milestones, price, warranties, liability and change terms.

Contract administration and closure

During administration, compare vendor progress and deliverables with milestones and quality terms, verify invoices, process approved changes, record issues and resolve claims. At closure, confirm contractual completion and acceptance, settle final amounts, document outstanding obligations and archive the agreement.

Typical software-contract terms

Scope of work; deliverables; schedule and milestones; contract price; payment terms; acceptance criteria; change control; quality standards; intellectual-property rights; confidentiality; warranties and support; liability; liquidated damages or penalties; termination; and dispute resolution.

Acceptance

Contract acceptance is the customer’s formal confirmation that delivered work meets the agreed requirements and acceptance criteria. The flow is: define criteria, deliver, inspect and verify, run UAT, log deficiencies, remediate, re-verify, issue written acceptance and settle the final payment.

  • Provisional acceptance: temporary approval while minor non-blocking defects are fixed.
  • Partial acceptance: approval of a completed subsystem or milestone.
  • Final acceptance: unconditional approval of all contractual requirements.
  • Conditional acceptance: approval subject to specified future obligations or remediation.

Acceptance criteria checklist

  • Functional requirements and agreed system behaviour.
  • System performance benchmarks and software quality standards.
  • Security and data-protection requirements.
  • UI/UX requirements and approved design criteria.
  • Technical and user documentation.
  • Architecture and technical specifications.
  • Successful test-case execution and agreed pass rates.
  • All critical and high-severity defects resolved.
  • Delivery within the agreed contractual timeline.

1. Effort estimation and sizing

HQ1. A new identity service has incomplete requirements, strict security needs and no close historical match. A director asks one senior engineer for a single number. Recommend a defensible estimation process and explain whether expert judgment or analogy should anchor it.

Answer

Use expert judgment as the primary anchor because no close analogue exists. First bound the scope and assumptions; collect independent ranges from security, architecture, development and testing specialists; compare the assumptions behind differences; reconcile a range; record risks and rationale; and later compare actual effort to calibrate estimates. A single senior estimate hides uncertainty and invites anchoring.

HQ2. A completed 400-FP banking service took 24 person-months. A new, comparable service is 500 FP, but its integration burden is estimated to be 15% higher. Calculate an analogy estimate and state the key assumption.

Answer

Scale for size: 24×(500/400)=30 PM. Apply the stated burden: 30×1.15=34.5 person-months. This assumes effort scales proportionally with function points over this range and that the 15% integration adjustment is justified.

MQ3. An estimate is needed before task details are stable, and system integration is significant. Later, the requirements and work breakdown become stable. Which sequence best fits?
A. Bottom-up first, then top-down.
B. Top-down first, then bottom-up.
C. Analogy first, then expert judgment.
D. Bottom-up at both stages because it is always more accurate.

Answer: B

Lead early with top-down estimation: it is quicker and captures system-level integration, but may overlook task detail. Once requirements and tasks are stable, use bottom-up: it is more traceable to work items but takes longer and depends on complete decomposition. Option D confuses detail with accuracy when the task breakdown is unstable.

HQ4. Counted functions are 10 average EI, 6 average EO, 5 low EQ, 4 average ILF and 2 low EIF. Calculate UFP and adjusted FP at DI=40. A review then raises DI to 55 without changing function counts; calculate the revised FP and percentage increase.

Answer

UFP=(10×4)+(6×5)+(5×3)+(4×10)+(2×5)=135. At DI=40, VAF=1.05 and FP=135×1.05=141.75. At DI=55, VAF=1.20 and FP=135×1.20=162. Increase=20.25 FP, or 20.25/141.75×100≈14.29%. Both DI values are within 0–70 and both VAFs within 0.65–1.35.

HQ5. For a Mark II count, ΣNᵢ=14, ΣNₑ=8 and ΣNₒ=12. Calculate FPI and effort at 8 Mark II FP per person-month. Why should this count not be run through Albrecht’s VAF?

Answer

FPI=(0.58×14)+(1.66×8)+(0.26×12)=8.12+13.28+3.12=24.52 Mark II FP. Effort=24.52/8=3.065 PM, approximately 3.07 PM. Mark II uses transaction inputs, entity references and outputs; Albrecht’s VAF adjusts an Albrecht UFP count and does not apply to Mark II.

HQ6. A 10-KLOC project is classified as organic. Using E=2.4×KLOC^1.05 and TDEV=2.5×E^0.38, calculate effort, development time and average staffing. What does the staffing result not tell you?

Answer

E=2.4×10^1.05=26.93 PM. TDEV=2.5×26.93^0.38=8.74 months. Average staffing=26.93/8.74=3.08 people. It is an average over the schedule, not the number of people required at every lifecycle phase.

HQ7. A prototype has 4 screens with 4 views and 7 data tables each, plus 2 reports with 6 sections and 5 tables each. Reuse is 10% and capability is Low. Classify, then calculate OP, NOP and effort.

Answer

Each screen is Medium (3–7 views and 4–7 tables; weight 2). Each report is Difficult (≥4 sections and 4–7 tables; weight 8). OP=(4×2)+(2×8)=24. NOP=24×90/100=21.6. Low PROD=7, so effort=21.6/7=3.086 PM.

2. Project planning and risk management

HQ8. A project has uncertain requirements, a critical-path supplier dependency and a new technology choice. Explain how the project manager should incorporate risk management into the project plan and identify which artifacts are baselined versus maintained.

Answer

Risk management is part of normal project management, not a separate final document. Prioritise stakeholder goals and clarify requirements; identify and assess supplier, technology and scope risks; assign owners, triggers and responses; include contingency in cost and schedule; define acceptance and change rules; and review the plan with stakeholders. Baseline the approved scope/deliverables, schedule and cost. Maintain the risk plan and register alongside them, with owners and responses linked to relevant baseline work.

MQ9. Classify these as hazard, risk or issue, then choose a suitable identification technique for the unfamiliar technical dependency: (a) an unsupported database server, (b) the likelihood and impact of its failure, (c) the server has failed.

Answer

(a) Hazard; (b) risk; (c) issue. For the unfamiliar dependency, use a cross-functional architecture/interface review with engineers and suppliers, supported by brainstorming and WBS review. A lessons-learned checklist can supplement this review but cannot replace analysis of the new interface.

HQ10. Three risks have exposure data: A has probability 0.6 and impact ₹50,000; B has 0.2 and ₹160,000; C has 0.4 and ₹70,000. Policy requires an active response at exposure ≥₹30,000. Calculate exposures, apply the boundary correctly and rank the responses.

Answer

A=₹30,000; B=₹32,000; C=₹28,000. A and B meet the inclusive ≥₹30,000 threshold; C does not. Rank B first, then A; monitor C under the lower-risk policy. This shows why both impact and probability, plus the exact threshold operator, matter.

HQ11. Match the response and control action: replace an unstable framework; train a team to lower error probability; use a managed cloud contract with explicit service liability; accept a minor documentation delay. For each, say what the risk owner should keep monitoring after the response.

Answer

Replace framework=avoid; training=mitigate; cloud agreement=transfer; minor delay=accept. In every case, retain an owner, trigger, status and review date in the risk register. Control continues by tracking indicators and residual exposure, checking mitigation effectiveness, identifying new risks, using contingency when triggered, and updating the register and stakeholders.

3. PERT and critical path

HQ12. An activity has optimistic time 4 days, most likely time 7 days and pessimistic time 16 days. Calculate expected time, standard deviation and variance. What ordering must the three estimates satisfy?

Answer

tₑ=(4+4×7+16)/6=8 days. σ=(16−4)/6=2 days; variance=σ²=4 days². Valid estimates must satisfy tₒ≤tₘ≤tₚ.

HQ13. Network: A(3) and B(4) start together; C(6) and D(2) follow A; E(5) follows both B and D; F(4) follows both C and E. Find project duration, all critical paths and total float for B and C.

Answer

Path lengths: A–C–F=13; A–D–E–F=14; B–E–F=13. Project duration=14 days, critical path=A–D–E–F. Backward pass gives B and C each 1 day total float. Both become critical if that float is consumed.

HQ14. In Q13, E is shortened from 5 to 3 days. Recalculate the finish date and critical path. Why is simply subtracting two days from the original project duration wrong?

Answer

New path lengths: A–D–E–F=12; A–C–F=13; B–E–F=11. The new duration is 13 days on A–C–F. Shortening E makes another path longest; the project only gains one day because the critical path shifts.

HQ15. A critical path has expected duration 32 days and activity variances 1, 0.25 and 2.25 days². Assuming independent durations and the normal approximation, find the probability of finishing within 34 days. Use P(Z≤1.07)=0.8577.

Answer

Project variance=1+0.25+2.25=3.5 days²; σ=√3.5=1.871 days. Z=(34−32)/1.871=1.07. Probability=0.8577 or 85.77%. This estimate depends on the stated independence and normal-approximation assumptions.

4. Monitoring, control and change

MQ16. A manager receives monthly spreadsheets with inconsistent dates and definitions. Design the minimum monitoring framework and choose a useful visual for (a) dependency timing and (b) trend or threshold exceptions.

Answer

Define approved baselines; metric definitions and status date; data owners and sources; collection frequency; validation rules; thresholds; reporting format; escalation path; and review cadence. Use a Gantt/milestone view for timing and dependencies, and a trend chart/dashboard for changes over time and threshold exceptions. Collect comparable data from work records, finance, issue/defect trackers, risk logs and approved change records.

HQ17. At the status date PV=₹120,000, EV=₹90,000, AC=₹105,000 and BAC=₹300,000. A further ₹18,000 is committed but not yet incurred. Calculate CV, SV, CPI, SPI and EAC if current cost efficiency continues. Should the commitment be added to AC?

Answer

CV=EV−AC=−₹15,000; SV=EV−PV=−₹30,000; CPI=90/105=0.857; SPI=90/120=0.75. The project is over budget and behind schedule in earned-value terms. EAC=BAC/CPI=300,000/0.8571≈₹350,000. Do not add the unincurred commitment to EVM AC; track it separately in cost monitoring and include it in the remaining-cost forecast as appropriate. This EAC assumes current cost efficiency continues.

HQ18. You can inspect only one item in a weekly monitoring review. Policy says first review any zero-float activity; otherwise review the item with the highest risk exposure. Item A is a zero-float migration with exposure ₹20,000; B has 2 days float and exposure ₹80,000; C has 5 days float and exposure ₹50,000. What is reviewed first, and why?

Answer

Review A first. The policy gives zero float priority before comparing exposure, and A is on the critical path. If no item had zero float, B would be selected because its exposure is highest.

HQ19. A critical integration task is late because the test environment was unavailable. Give the recovery sequence and explain when the schedule may be rebaselined.

Answer

Confirm deviation; find root cause; assess impact on dependencies, cost, quality and delivery; compare feasible corrective actions; get required approval; implement; monitor recovery. Rebaseline only after authorised approval of a legitimate plan change. Changing the baseline first would conceal the original variance.

HQ20. An urgent security fix is requested after baseline approval. Place these actions in order and state why work should not start merely because a request was received: impact analysis, submit/log request, approve or reject, update baseline, implement, verify and monitor.

Answer

Submit and log → impact analysis → approve/reject through the authorised urgent route → update affected baseline and records after approval → implement → verify → monitor. A request is not approval; starting early can create unapproved scope, cost, schedule and acceptance obligations. An emergency route can accelerate review while preserving authority and traceability.

5. Contracts and acceptance

HQ21. Select a contract type for each case and identify who bears more cost risk: (a) stable payroll scope with objective acceptance tests, (b) uncertain research, (c) variable specialist hours, and (d) a known price per migrated record but uncertain volume.

Answer

(a) Fixed-price; supplier bears more cost risk if scope is controlled. (b) Cost-reimbursement; buyer bears more cost risk. (c) Time and materials; payment follows hours/rates, so buyer exposure depends on controls. (d) Unit-price; rate per unit is known but total cost changes with quantity.

HQ22. Put the contract-placement stages in order: negotiate, define needs, evaluate bids, prepare contract documents, award, invite tender/RFP/RFQ, receive supplier proposals, sign, administer and close. Name two evaluation criteria.

Answer

Define needs → prepare documents → invite tender/RFP/RFQ → receive proposals → evaluate → negotiate → award → sign → administer → close. Evaluation criteria include technical capability, price, delivery feasibility, past performance, team qualifications and risk. Contract administration tracks deliverables, milestones, invoices, quality and approved changes; closure confirms acceptance, settles payments/claims and archives records.

MQ23. A draft software contract names a price and delivery date but says nothing about what will be delivered, how it will be accepted, ownership of source code, or handling of defects after launch. Name the missing terms most directly required.

Answer

Add scope of work and deliverables; measurable acceptance criteria; intellectual-property rights; and warranties/support. A complete contract should also specify milestones/payment, change control, quality, confidentiality, liability, penalties, termination and dispute resolution.

HQ24. During administration, the customer signs off one completed subsystem while the rest continues; later the whole system is accepted with minor non-blocking defects to be fixed by an agreed date; another approval is made subject to regulator clearance. Identify the acceptance types and state the key control steps.

Answer

The subsystem sign-off is partial acceptance. Temporary sign-off of the whole system with minor defects is provisional acceptance. Approval subject to regulator clearance is conditional acceptance. Final acceptance is unconditional confirmation that all requirements are met. Define criteria before delivery; inspect and run UAT; log deficiencies; require fixes and re-verification; obtain written sign-off; then settle final payment and close the contract when obligations are complete.
