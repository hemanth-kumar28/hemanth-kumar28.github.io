01

SSA/SD and DFD decomposition

The main long-answer and drawing topic
Module 3
Likely wording
“Explain Structured Systems Analysis and Structured Design. Describe DFD representation, decomposition and balancing, and illustrate the process using a suitable system.”

Structured Systems Analysis (SSA) builds a problem-oriented, functional model: what data enters, how processes transform it, where data is stored, and what leaves the system. A DFD does not itself prescribe a program hierarchy or execution order; levelling organizes detail across diagrams. Structured Design (SD) then converts the analysis into a modular, call-and-return solution, commonly shown with a structure chart. In short: SSA emphasizes what the system must do; SD organizes how software modules will do it.

DFD building blocks

External entity supplies or receives data. Process transforms data. Data flow is labeled data in motion. Data store holds data for later use.

Supporting representations

DFDs are supported by a data dictionary and process specifications. Leaf-process logic can use structured English, decision tables or decision trees. SD commonly uses a structure chart.

Balancing rule: when a process is expanded, preserve the data that crosses its boundary. Its lower-level diagram must account for its parent-level inputs and outputs. “Level 0” numbering varies across texts; use the convention your lecturer expects.

Keep the notation straight: DFD arrows represent data moving between processes, stores and external entities. They do not mean that one process calls another. DFD levelling is functional decomposition, not machine flowcharting.

Home Safety and Security System: context diagram

Illustrative scope: sensors report events; the homeowner changes modes and views alerts; a monitoring service receives alarm reports.

Level 1: divide the system into processes

One reasonable decomposition is five processes. In an exam drawing, number the processes and label every data flow. Keep the diagram readable; a “3–7 bubbles” rule is a useful decomposition heuristic in some teaching materials, not a universal law.

1.0 Manage modes

Accept authorized mode/configuration commands and update the zone or arming configuration.

2.0–3.0 Detect and assess

Validate sensor reports, look up sensor details and apply the current zone/mode rules.

4.0–5.0 Respond and record

Send alarm/notification data, record outcomes and return requested event history.

How the DFD is divided and checked
  1. Set the boundary and list external entities and their inputs/outputs.
  2. Draw one context process for the whole system.
  3. Identify the system’s major functions and expand the context process into a top-level DFD.
  4. Explode only processes that need more detail; preserve the parent’s incoming and outgoing flows.
  5. Continue until a leaf function can be described as a simple algorithm; write a mini-spec for it.
  6. Cross-check coverage against requirements and the dictionary; remove unsupported flows and missing transformations.

DFDs do not show: execution order, timing, or detailed decision logic. Add a mini-spec, state/behavior model or control-flow representation if those details matter.

SSA/SD heuristics from the Module 3 lecture
  • Start with system inputs and outputs because they are often clearest in the requirements; work inward from the boundary, or outward from the central functions when that is more useful.
  • Use consistent, meaningful labels for every process and flow.
  • Keep exception and error handling out of the first functional model when it would obscure the normal data transformations; add it during design refinement.
  • Do not turn a DFD into a flowchart: model data movement and transformations, not machine operation sequence.
  • DFD levelling and the choice of a central transform are guided by heuristics; justify a clear, balanced decomposition rather than claiming one universal split.

Transform analysis

Use when data follows a transformation pipeline. Identify input, central transformation and output portions; map them to modules and refine by factoring.

Transaction analysis

Use when a request/event type selects a different path. Add a transaction centre, then one branch per transaction type—for example, sensor event, mode command or history request.

How the DFD is divided: transaction analysis separates the top-level model into tractable submodels for distinct event or request types. The SSAD case-study deck shows the partition boundary as a dotted line; data flows can cross it, so shared data must remain explicit. Apply transform analysis to each transaction DFD, then merge the resulting structure charts and add a top-level selector where needed.
Structure-chart mapping: the central transform becomes the controlling/main module; more abstract operations sit higher, while concrete device input/output procedures sit near the bottom. DFD data-flow arcs become module invocation/control links, with required data passed through interfaces. Aim for cohesive modules and low coupling, then merge transaction charts, add a selector if needed and rationalize duplicated work.
02

Data Dictionary construction

A likely stand-alone question, already connected to the DFD case
10–15 marks
Likely wording
“Define a Data Dictionary. Explain its contents, notation and construction. Construct dictionary entries for the data flows and stores in a given system.”

A data dictionary is a structured catalogue of the data named in the analysis model. It defines data flows, data stores and their component data items. It gives analysts and developers a shared vocabulary and supports consistency checks across the DFD hierarchy.

Typical entry fields

Name

Preferred unique term used consistently in the DFD.

ExampleSENSOR_EVENT

Alias

Alternative names found in requirements or user language.

ExampleDetector report

Where-used / how-used

Processes or stores using the item, and whether it is read, created or updated.

ExampleCreated by 2.0; consumed by 3.0

Content

Composition of a composite flow or store.

Examplesensor_id + event_type + event_time

Logical constraints

Meaning, allowed categories, dependencies or rules needed to interpret the data.

Exampleevent_type is one of the domain event categories
Abstraction rule from the course text: keep definitions at the problem level. Explain what data means and how it is composed; do not make the dictionary a physical database schema or specify byte layouts and storage formats unless the problem explicitly requires them.

Notation to memorize

=
“is defined as” or “is composed of”
+

Notation caution: dictionary conventions differ between texts. In the Yourdon-style convention shown here, parentheses mean optional and square brackets enclose alternatives. If your lecturer’s notes define the symbols differently, reproduce that convention in the exam.

Worked entries: Home Safety and Security System

SENSOR_EVENT = sensor_id + zone_id + event_type + event_time + reading
event_type = [DOOR_OPEN | WINDOW_OPEN | MOTION | SMOKE | CO | PANIC]

SENSOR_RECORD = @sensor_id + zone_id + sensor_type + location + enabled_flag
SENSOR_REGISTRY = {SENSOR_RECORD}

USER_COMMAND = user_id + command + command_time + (zone_id)
command = [ARM | DISARM | CHANGE_PROFILE | REQUEST_HISTORY]

ALARM_REPORT = event_id + alarm_type + zone_id + event_time + response_status
EVENT_LOG = {event_id + SENSOR_EVENT + threat_level + action_taken}
How to construct the dictionary from a DFD
  1. Collect every data item named in the DFDs, process specifications and other analysis descriptions.
  2. Define composite items in terms of their component items and explain elementary items by their logical meaning and necessary domain rules.
  3. Record aliases and where/how the item is used.
  4. Use one name consistently, and check each flow’s input/output composition against the processes and stores it touches.
  5. Keep the dictionary synchronized when a DFD is changed.

The dictionary defines what the data means and contains. A process mini-spec defines what a leaf process does.

03

Attribute-Driven Design (ADD)

The core Module 4 architecture method
Module 4
Likely wording
“Explain ADD, define architectural drivers, and discuss the ADD steps with a suitable case study.”

Attribute-Driven Design (ADD) is an iterative method for translating architectural drivers into software structures and design decisions. The supplied book gives the detailed ADD 3.0 process below. It treats architecture design as a series of design rounds, with focused iterations that address prioritized drivers and produce structures, decisions and views.

2000 · ADD 1.0First published as Architecture-Based Design (ABD).
2006 · ADD 2.0Linked quality-attribute scenarios to structures through tactics and patterns.
2013 · practical bridgeThe authors use “ADD 2.5” informally for framework guidance; it is not a separately official version.
ADD 3.0 · supplied bookRefines the method using practice: purpose, reuse, implementation options, analysis and documentation.

Inputs and architectural drivers

First clarify the design purpose: an early estimate, an exploratory prototype, or design for construction and release can require different levels of detail. Then review the primary functionality, prioritized quality-attribute scenarios, constraints, architectural concerns and—when evolving a system—its existing design. Drivers are the requirements and concerns selected to shape architectural choices.

Primary functionality

Important use cases or capabilities that require a structural solution.

Quality attributes

Prioritized, measurable scenarios for performance, availability, security, modifiability and other qualities.

Constraints

Technology, policy, budget, integration, regulatory or deployment limits.

Architectural concerns

Internal needs such as testability that may matter even when stakeholders did not state them as requirements.

Existing architecture

For a brownfield system, inspect the elements and decisions that are already in place.

Purpose

Decide whether the design is for estimation, risk exploration, a project increment or a releasable system.

ADD 3.0 process: the book’s answer sequence

STEP 1

Review inputs

Confirm the design purpose, key use cases, prioritized quality scenarios, constraints, concerns and existing design, if any.

STEP 2

Set the iteration goal

Select the prioritized drivers this design iteration will address; record the goal in the design backlog.

STEP 3

Choose elements to refine

Select the elements involved in those drivers. Refine by decomposition, combination or improvement.

STEP 4

Choose design concepts

Select suitable reference architectures, patterns, deployment patterns, tactics, frameworks, technologies or external components.

STEP 5

Instantiate and connect

Create architectural elements, allocate responsibilities, establish relationships and define their interfaces.

STEP 6

Sketch views and decisions

Capture the structures and record significant decisions with their rationale so they can be communicated and reviewed.

STEP 7

Analyze and review

Check whether the design meets the iteration goal and advances the overall design purpose; invite another perspective where possible.

STEP 8

Iterate if necessary

Use risk and driver priority to decide what remains. Address critical drivers or establish that the design is good enough for its purpose.

Sequence nuance: the book lists driver selection before element refinement, but explains that Steps 2 and 3 can be reversed in some contexts, such as starting from a reference architecture. Keep the overall ADD 3.0 steps distinct from older ADD 2.0 summaries.

Case application: Home Safety and Security System

Availability Internet is lost during a smoke event

Decision

Keep event assessment and alarm activation on the home hub; queue remote alerts.

Check

Confirm that local alarm response continues without cloud access.

Performance Intrusion needs fast response

Decision

Give alarm events a short, direct processing path and priority over history/report requests.

Check

Measure sensor-event-to-siren delay under expected load.

Security An unauthorized user tries to disarm

Decision

Authenticate commands, authorize mode changes and record denied attempts.

Check

Test denied commands and verify audit records.

Modifiability A new sensor type is introduced

Decision

Use sensor adapters to normalize device-specific reports into a common event format.

Check

Check whether a new adapter can be added without changing threat rules.

Constraint Hub and sensors have limited resources

Decision

Choose lightweight local processing and define backup-power behavior.

Check

Compare resource use and backup run-time with agreed requirements.

Exam tip: Do not stop after listing steps. Show the chain requirement → driver → design decision → component responsibility/interface → verification for at least two drivers.
ADD 3.0 compared with ADD 2.0

ADD 3.0 is an evolution of ADD 2.0, not a wholly different method. ADD 2.0 was useful for selecting and combining tactics and patterns to address quality-attribute scenarios, but gave less guidance on starting a design, choosing a design purpose, reusing reference architectures, addressing implicit concerns, or connecting abstractions to implementation choices.

ADD 3.0 makes design purpose and input review explicit; permits critical requirements to guide element selection; encourages short iterations and possible implementation spikes, reference-architecture and framework reuse, and concrete implementation options; and makes analysis, view sketches, decisions and rationale explicit. The book calls “ADD 2.5” its own informal label for an intermediate practical revision, not a separate official version. ADD 3.0 is the version detailed by the supplied book and reflected in the Module 4 slides.

Architecture foundations: the short answer that strengthens an ADD response

Software architecture is the set of structures needed to reason about a system: its software elements, the relationships among them, and properties of both. Architecture design makes decisions that translate needs and constraints into solution structures. Its scope is distinct from later element-interaction design (detailed collaborations and interfaces) and element-internals design (the inside of an individual element).

Why architecture matters

It enables or inhibits driving qualities, supports early prediction and change analysis, communicates hard-to-change decisions, constrains implementation, shapes teams, and supports prototypes, cost/schedule reasoning, reuse and complexity control.

Architect’s work

Lead, communicate and negotiate; maintain technical and project skills; analyze risk and trade-offs; prioritize drivers; choose and justify concepts; allocate responsibilities; review decisions and check conformance.

Design artifacts

Sketch views of structures and record decisions with rationale during design; refine and formalize documentation as the design matures.

Exam connection

Use the architecture definition, then trace a prioritized scenario into a design decision, an element/interface and a way to analyze or verify it.

JSP and JSD

Jackson methods: structure the program, then model the event-driven system
Module 3
Likely wording
“Explain JSP and JSD, including their model, representation forms, processes and heuristics. Compare the two methods.”

Michael Jackson’s methods focus on the subject matter and the ordering of data/events before the software structure. JSP is chiefly a program-design method for sequential input and output streams. JSD extends the approach to model real-world entities and their time-ordered event histories at system level.

Memory hook: JSP

Program structure is derived from the structures of the input and output data streams.

Memory hook: JSD

System model begins with entities and events in the real world, then adds functions and implementation decisions.

JSP: representations and process

JSP describes data structures with three constructs: sequence, selection and iteration. The design compares the structures of input and output streams, identifies correspondences, and merges them into a program structure.

JSP heuristics and structure clashes
  • Represent the actual input and output structures faithfully; do not distort them just to simplify implementation.
  • Establish input/output correspondences before allocating operations.
  • Recognize clashes rather than forcing unrelated structures into a single traversal.

Boundary clash

Input and output groups start or end at different boundaries.

Typical responseSplit into processes and communicate at suitable common units.

Ordering clash

Corresponding items occur in different orders.

Typical responseUse an intermediate structure, buffer or reorder the data.

Interleaving clash

Several entity-specific sequences are interwoven.

Typical responseSeparate streams into entity processes, then coordinate or recombine results.

JSD: model, representations and six steps

The JSD model focuses on real-world entities, the events/actions they participate in, the time ordering of those events, and the attributes that change as events occur. Functions such as reports are added after the model is defined.

COURSE PHASE 1

Modeling

Identify entities and actions, then describe the time-ordering of each entity’s actions and relevant attributes.

COURSE PHASE 2

Network

Turn entity models into communicating processes and add functions that produce required system outputs.

COURSE PHASE 3

Implementation

Introduce system timing and map the abstract process network to schedulers, modules and physical resources.

The course deck’s three phases map to the six textbook steps: Entity/Action → Entity Structure → Initial Model → Function → System Timing → Implementation.

JSD representation forms used in the course

Entity Structure Diagram (ESD)

Shows an entity’s actions and their sequence, selection or repetition in its life history.

System Specification Diagram (SSD)

Also called a network diagram; shows entity and function processes and how they communicate.

System Implementation Diagram (SID)

Maps the abstract process network to a realizable implementation, including scheduling; processes may be combined to fit available resources.

Illustrative Zone entity history

ZONE_LIFE = REGISTER + {ZONE_SESSION}
ZONE_SESSION = [ARMED_SESSION | DISARMED_SESSION]
ARMED_SESSION = ARM + {SENSOR_EVENT} + DISARM
SENSOR_EVENT = [DOOR_OPEN | MOTION | SMOKE | CO]
ALARM_RESPONSE = ALARM_RAISED + (ALARM_ACKNOWLEDGED) + ALARM_RESET

This is a simplified event-history sketch. In a real JSD model, define the entities, event meanings, attributes and ordering constraints from the actual requirements.

JSD heuristics and exam comparison
  • Start from relevant real-world events, not only from a feature list.
  • Make each entity’s event order explicit; define attribute changes through the events that cause them.
  • Build the real-world model first; add functions/reporting processes around information in the model.
  • Model process communication and timing before settling implementation and scheduling.

Six parts of a quality-attribute scenario

The phrase “six parts of quality attributes” most likely points here
Module 4
Likely wording
“What is a quality-attribute scenario? Explain its six parts and formulate a concrete scenario for a suitable system.”
Terminology: these are the six parts of a quality-attribute scenario—not six quality attributes. Performance, availability, security, modifiability and usability are examples of quality attributes.

A quality-attribute scenario turns a vague requirement into a specific, testable statement about system behavior. Its core is a stimulus–response pair, with a response measure; source, artifact and environment complete the description. Complete example: availability

Source
Smoke sensor
Stimulus

Artifact

Write it as a sentence: “When a smoke sensor reports a reading above its configured threshold while mains power and internet service are unavailable, the local alarm subsystem activates the audible alarm within 1 second, continues for at least 30 minutes on backup power, and sends its queued remote notification within 30 seconds after connectivity returns.”

The numeric thresholds above are illustrative. Real targets must be agreed with stakeholders. The exam point is to make the response measurable, rather than saying only “quickly” or “reliably.”

Exam extension: prioritize scenarios and connect them to architecture

Rank each scenario on two separate dimensions: importance to system success (customer/stakeholder view) and technical risk (architect’s view), using low, medium and high. Address high/high, high/medium and medium/high scenarios first.

A utility tree organizes Utility → quality attributes → system-specific refinements → concrete scenario leaves; prioritize the leaves. A facilitated Quality Attribute Workshop (QAW) helps stakeholders elicit, refine, prioritize and agree on these scenarios. In ADD, selected scenarios become drivers that guide design choices and later analysis.
