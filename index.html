1Albrecht Function Point Analysis

Measuring software by what it does for the user, not by how much code it takes

1.1 What it is and why it exists

Function Point Analysis (FPA) is a method of measuring the size of a piece of software in terms of the functionality it delivers to the user, rather than in terms of its technical implementation. It was introduced by Allan J. Albrecht at IBM in 1979, and later taken over and standardised by the International Function Point Users Group (IFPUG).

The motivation was a practical problem with the older unit of size, lines of code (LOC):

  • LOC is language dependent. The same payroll system may take 20,000 lines in C and 4,000 lines in a fourth-generation language. The user gets the same system, but the "size" differs fivefold.
  • LOC cannot be known early. You only know how many lines you wrote after you have written them, which is exactly when the estimate is no longer needed.
  • LOC rewards bad work. A verbose, badly factored programmer produces more "size" and therefore appears more productive.
  • LOC means nothing to the customer. A user cannot confirm whether 20,000 lines is the right amount; a user can confirm "the system has 10 input screens and 6 reports."

Function points solve all four. They are counted from the requirements or design documents, before a single line of code exists, and they describe the system in terms the user recognises.

Definition to memorise

A function point is a unit of measurement that expresses the amount of business functionality an information system provides to a user, independent of the technology used to implement it.

1.3 The five function types — fully expanded

Albrecht's method identifies five function types, abbreviated EI, EO, EQ, ILF and EIF. They split into two families. Getting this split right is usually worth a mark on its own.

  • Transactional functions — what the system does: EI, EO, EQ.
  • Data functions — what the system stores or reads: ILF, EIF.

Everything is counted relative to the application boundary — an imaginary line separating the system being measured from the users and other systems around it. "External" always means "crosses the boundary".

The five function types with full names, definitions and examples
CodeFull nameWhat it isExamples
EIExternal InputA process where data or control information enters the system from outside the boundary and maintains one or more internal files, or changes system behaviour. Data flows inward."Add new customer" form; "Update stock quantity"; batch file import; delete order.

EIFExternal Interface FileA user-identifiable group of logically related data that this application reads but does not maintain — it is owned by some other application.Currency rates maintained by the treasury system; an employee master owned by the HR system.
The distinction examiners test most

EO versus EQ. Both send data out. The question is whether anything happens on the way. If the system calculates, derives, totals, or updates a file in the process, it is an External Output. If it simply fetches stored data and displays it unchanged, it is an External Inquiry. "Display the invoice as stored" is an EQ; "Display the invoice with GST computed and a running balance" is an EO.

ILF versus EIF. Ask one question: does my application write to it? If yes, ILF. If my application only reads it and some other system owns it, EIF. Note that the same physical table can be an ILF for one application and an EIF for another.

Memory hook

In, Out, Ask, Own, Borrow. EI = data comes in. EO = data goes out after work is done on it. EQ = the user asks and gets back exactly what is stored. ILF = data the system owns. EIF = data the system borrows.

1.6 The 14 General System Characteristics and the Value Adjustment Factor

UFP measures functionality. It says nothing about the technical environment the software must live in. A 135 UFP system that runs on one desktop is not the same job as a 135 UFP system that must be distributed across five sites, respond in under a second and be installable by non-technical staff.

Albrecht's original method therefore adds 14 General System Characteristics (GSCs). Each is rated on a 0 to 5 scale for its Degree of Influence (DI).

DI = Σ Fᵢ    (the sum of the 14 individual degree-of-influence ratings)

VAF = 0.65 + 0.01 × DI

Minimum DI = 14 × 0 = 0  →  VAF = 0.65 + 0.00 = 0.65
Maximum DI = 14 × 5 = 70  →  VAF = 0.65 + 0.70 = 1.35

Therefore 0.65 ≤ VAF ≤ 1.35. The environment can shrink or grow the count by at most 35%.
Why 0.65 and why 0.01

The constants are chosen so that an "average" system — every characteristic rated 3, giving DI = 42 — lands almost exactly on VAF = 1.07, and the whole adjustment is capped at ±35%. Albrecht deliberately limited the swing so that environmental judgement could never dominate the measured functionality. If an exam asks you to justify the range, that is the answer: the adjustment is bounded so the count stays a size measure, not an opinion.

FP = UFP × VAF

1.8 The Function Point Analysis process

Identify→Classify→Weight→Adjust→Calculate
  1. Identify the functionsDraw the application boundary. Walk the requirements and list every EI, EO, EQ, ILF and EIF.
  2. Determine the complexity of eachCount DETs, FTRs and RETs, then read Low / Average / High off the matrices in §1.4.
  3. Calculate the Unadjusted Function PointsMultiply each count by its weight and sum: UFP = Σ (count × weight).
  4. Rate the 14 General System CharacteristicsScore each from 0 to 5 and add them to get the Degree of Influence, DI.
  5. Calculate the Value Adjustment FactorVAF = 0.65 + 0.01 × DI, which must fall between 0.65 and 1.35.
  6. Calculate the final Function Point countFP = UFP × VAF. Use this as the size input to effort, cost and schedule estimation.

1.9 What you do with FP once you have it

Effort (person-months) = FP ÷ Productivity (FP per person-month)

2Additional Estimation Methods

Using informed people, comparable projects and transaction structure to estimate before the code exists

2.1 Why estimates are made in stages

An estimate is a reasoned prediction of the effort, duration or cost needed to deliver a defined scope. It is not a promise. Early in a project the scope and technical solution are uncertain, so the estimate should be expressed as a range with assumptions and refined as evidence improves.

2.2 Expert judgment

Definition

Expert judgment is an estimate produced by people who have relevant technical, domain or project experience. The expert uses knowledge of similar work, constraints, productivity and likely risks to predict effort, duration or cost.

Expert judgment is often the only practical method when the product is new, the requirements are incomplete, or historical measurements are weak. It becomes much stronger when the expert states the basis of the estimate instead of supplying one unexplained number.

  1. Define the item being estimatedState the deliverable, boundaries, unit and level of detail. “Build the payment service” is too vague; “design, code, test and document the payment API” is estimable.
  2. Choose people with relevant experienceInclude technical, domain, testing, operations and project-management perspectives where each affects the work.
  3. Estimate independentlyAsk each expert for a most-likely value or a three-point range before discussion. Independent estimates reduce anchoring on the first number spoken.
  4. Expose assumptions and differencesCompare the estimates, identify why they differ, and separate scope differences from genuine uncertainty.
  5. Reconcile the estimateUse a moderated discussion or a Delphi-style anonymous second round until the group can explain the chosen range and its risks.
  6. Record and reviewDocument the estimate, assumptions, confidence, evidence and owner. Compare actual results later so future judgment becomes calibrated rather than anecdotal.

Delphi-style judgment

In a Delphi technique, experts estimate separately, a moderator shares an anonymous summary, and the experts revise their estimates after discussing the assumptions. The process is repeated until the spread is acceptable or the reasons for disagreement are understood. It prevents the most senior or most confident person from dominating the first round.

Exam distinction

“Expert judgment” is a method, not a single person’s guess. A defensible answer mentions relevant experts, independent estimates, assumptions, reconciliation, documentation and later comparison with actual performance.

2.3 Estimation by analogy

Definition

Estimation by analogy predicts a new project from the measured effort or cost of one or more completed projects that are similar in size, technology, domain, team capability and delivery conditions.

The method is more than saying “the last project took six months.” The estimator must identify what is similar, quantify the difference, and adjust for changed technology, scope, team productivity, reuse, integration or quality requirements.

  1. Select a reference projectChoose a completed project with reliable actual data, not merely a project with a similar name.
  2. Compare the driversCompare size, requirements volatility, architecture, interfaces, team experience, tools, quality target, reuse and schedule pressure.
  3. Scale for the size differenceUse a size ratio when the relationship is reasonably proportional.
  4. Apply explicit adjustmentsIncrease or decrease the result for identified differences, and state whether the adjustment is a percentage or a fixed amount.
  5. Cross-check and give a rangeCompare with another analogue or an independent expert estimate, then report the uncertainty rather than false precision.
Estimatenew = Estimatereference × (Sizenew ÷ Sizereference) × Adjustment factors
The size ratio is only a starting point; the adjustment factors make differences explicit.
Worked example — adjusted analogy

A completed project delivered 400 function points in 24 person-months. The new project is estimated at 500 function points and has an integration burden assessed as 15% higher.

Size-scaled estimate = 24 × (500 ÷ 400) = 24 × 1.25 = 30 person-months.

Adjusted estimate = 30 × 1.15 = 34.5 person-months.

The answer is not “34.5” alone. State the reference project, the size measure, the integration assumption and a confidence range around the result.

2.4 Function Point Mark II

What Mark II changes

Mark II Function Point Analysis is a functional-size method associated with Charles Symons and standardised as ISO/IEC 20968. It views an application as a set of logical transactions, each with an input, processing of referenced data entities, and an output. It counts input data elements, referenced entity types and output data elements instead of using Albrecht’s five function types and Low / Average / High complexity matrices.

The method is still based on user-visible business functionality and a defined application boundary. The important difference is the counting model: processing complexity is represented by the number of data entities referenced by each logical transaction, while input and output work is represented by their data-element counts.

3COCOMO and COCOMO II

From classic KLOC-based cost estimation to application composition with screens, reports and components

3.1 The general COCOMO idea

COCOMO — the Constructive Cost Model — is an algorithmic software cost-estimation family developed by Barry Boehm. It starts with an estimate of software size, usually in KLOC (thousands of delivered lines of code), and converts that size into effort and development time. The model makes the cost drivers visible instead of hiding them inside one unexplained total.

The key idea

Size is the main driver, but effort is not perfectly linear. A larger system usually needs disproportionately more effort because of communication, integration, coordination, testing and management overhead.

Object point

An object point is a weighted count of the user-visible building blocks of an application — screens, reports and third-generation-language components — where the weight reflects how hard each one is to build. It is not the same thing as an object in object-oriented programming.

3.3 The seven steps

  1. Assess the object countsCount the number of screens, reports and 3GL components the application will contain.
  2. Classify the complexity level of each objectUsing the tables in §3.4, label each screen and report as simple, medium or difficult.
  3. Assign complexity weightsLook up the weight for each object from the weight table in §3.5.
  4. Determine the object point countObject points = Σ (number of instances × weight). Add up all weighted object instances.
  5. Compute new object pointsDeduct the percentage of functionality being reused: NOP = OP × (100 − %reuse) / 100.
  6. Determine the productivity rateRead PROD from the productivity table using developer experience and capability.
  7. Compute the estimated effortEffort = NOP ÷ PROD, expressed in person-months.

3.7 The full worked example

Problem

Consider a database application project with the following characteristics:

  • The application has 4 screens with four views each, and screen data tables for 3 servers and 4 clients.
  • The application generates 2 reports of six sections each, drawn from seven data tables for 2 servers and 3 clients.

4Project Planning

The six activities that turn an approved idea into an executable plan, with risk built into every decision

Project planning is the process of defining what will be delivered, by whom, by when, at what cost, and with what risks accepted. The output is a project plan that acts as the baseline against which everything later is monitored and controlled.

4.1 Project management in risk management

Risk management is not a separate document handed to the project manager at the end of planning. It is a project-management activity woven through scope, schedule, cost, quality, resources, procurement and stakeholder decisions. Every important planning decision should make its assumptions and uncertainties visible.

Plan the work→Identify uncertainty→Assess exposure→Choose responses→Monitor triggers→Update the plan

The project manager’s role

The project manager does not personally solve every risk. The manager makes risk ownership explicit, ensures responses are funded and scheduled, keeps the register connected to the baseline, and escalates exposures beyond the agreed tolerance. This is why risk management belongs inside project governance rather than beside it.

  1. Identify and meet with stakeholdersA stakeholder is anyone affected by, or able to affect, the project — sponsors, end users, operations staff, regulators, suppliers. Meeting them early surfaces conflicting expectations while they are still cheap to reconcile, and establishes who has authority to approve changes later.
  2. Set and prioritise goalsStakeholder needs are turned into project objectives. Because they will conflict — "fast", "cheap" and "complete" rarely coexist — they must be prioritised, not just listed. Goals should be specific and measurable so that completion can be judged objectively.
  3. Define deliverablesState the concrete products the project will hand over: the software itself, user manuals, training material, test reports, migration scripts. Each deliverable gets an acceptance criterion and an estimated delivery date. This is also where the scope boundary is drawn — writing down what is out of scope prevents scope creep later.
  4. Create the project scheduleBreak deliverables into activities, estimate the duration of each, establish dependencies, allocate resources, and build the network and Gantt chart. This is where PERT and CPM are applied, and where the critical path is identified.
  5. Identify issues and complete a risk assessmentList what could go wrong, assess probability and impact, calculate risk exposure, and decide a response for each significant risk. The output is the risk register. No plan is credible without this step, because a schedule with no contingency is a schedule that assumes nothing will go wrong.
  6. Present the project plan to stakeholdersWalk stakeholders through scope, schedule, budget, risks and assumptions, and obtain formal sign-off. Once signed off, the plan becomes the baseline; from that moment any alteration must go through change control.
Why the order matters

Each step consumes the output of the one before. You cannot schedule what you have not defined as a deliverable; you cannot define deliverables without prioritised goals; you cannot prioritise goals without knowing whose goals they are. If an exam asks you to justify the sequence, that dependency chain is the answer.

5Hazard Assessment

Finding the sources of harm and putting numbers on them

5.1 Hazard versus risk

Two definitions that must not be blurred

Hazard: a potential source of danger, or a condition that may cause harm to the software or the project. A hazard is a thing — an unstable technology, an unclear requirement, a single point of failure.

Risk: the combination of the likelihood that the hazard causes harm and the severity of that harm. A risk is a measured quantity.

Put simply: the hazard is the loose wire; the risk is how likely it is to start a fire and how much the fire would cost.

5.2 What hazards lead to

If a hazard is not controlled, the consequences for a software project typically fall into these categories:

  • Project delay — milestones and the final delivery date slip.
  • Cost overrun — the budget is exceeded, often through rework and overtime.
  • Poor quality — defects escape to production because testing was compressed to protect the date.
  • Failure to meet requirements — the delivered system does not do what the user needed.
  • Loss of data — through hardware failure, faulty migration or inadequate backup.
  • Security problems — breaches, unauthorised access, regulatory penalties.
  • Project cancellation — the most severe outcome, where sunk cost is written off entirely.

5.3 The assessment process

Hazard assessment

A systematic process of identifying hazards, analysing their likelihood and impact, and deciding how they should be controlled.

Identify→Analyse→Evaluate

Identify — what could go wrong

Techniques: checklists from past projects, brainstorming with the team, structured interviews with stakeholders, decomposition of the work breakdown structure, and lessons-learned records. Typical software project hazards:

Analyse — how likely and how bad

For each identified hazard, determine two quantities:

  • Probability — the likelihood that the hazard actually occurs. Expressed as a value from 0 to 1, or on a scale such as Very Low / Low / Medium / High / Very High.
  • Impact — the severity of the consequence if it does occur, measured in delay, money, or on a 1–5 severity scale.
Risk Exposure (RE) = Probability × Impact
Also written as Risk Exposure = Probability of unsatisfactory outcome × Loss if the outcome is unsatisfactory.

Worked illustration: a hazard with a 0.3 probability of occurring and an impact of ₹20,00,000 has a risk exposure of 0.3 × 20,00,000 = ₹6,00,000. That figure is what you can justifiably spend on preventing it — spending more would cost more than the risk itself.

6Risk Planning and Response Strategies

Deciding what to actually do about each risk

Risk planning

The process of deciding what actions should be taken to reduce the probability or the impact of an identified risk.

Identify risk→Analyse→Prioritise→Develop response strategies→Assign responsibilities→Monitor, review and update

Notice the last step loops. Risk planning is not a one-off document produced at kick-off; the register is revisited at every review point because old risks close and new ones appear.

6.1 The four risk response strategies

This is the single most reliably examined item in the risk topic. Learn the four names, the one-line definition, and a software example for each.

The four strategies, with what each one changes
StrategyWhat you doWhat it changesExample
1. Risk avoidanceChange the plan so the risk is eliminated completelyProbability drops to zeroA new technology is highly unstable, so you drop it and use a well-tested technology instead
2. Risk reduction
(mitigation)		Take action to reduce the probability or the impact of the riskProbability and/or impact fall, but the risk remainsProvide training to reduce errors caused by lack of technical skill; add automated regression tests

The test for acceptance

Acceptance is correct when the potential impact is small, or when the cost of controlling the risk exceeds the risk exposure itself. Spending ₹10,00,000 to prevent a risk whose exposure is ₹6,00,000 is not prudence, it is waste. Acceptance is a decision, not neglect — it is still written into the register with a named owner and a trigger for review.

Memory hook

A-M-T-A: Avoid, Mitigate, Transfer, Accept. Read them as a decreasing ladder of control: remove it, shrink it, hand it over, live with it.

6.2 Assigning responsibility

Every risk in the register gets a named owner — the person accountable for watching the trigger conditions and invoking the response. A risk owned by "the team" is owned by nobody. The owner is also responsible for reporting the risk's current status at reviews.

7Risk Control

Keeping identified risks inside acceptable limits while the project runs

Risk control

The activity of continuously monitoring identified risks and taking corrective action when necessary, so that risks stay within the limits the project has agreed to tolerate.

Monitor→Compare→Take action→Update

Monitor the risk indicators; compare the current position against the plan and the agreed tolerance; take corrective action where the comparison shows a breach; update the register and the plan to reflect what changed.

7.1 The seven risk control activities

  1. Track risk indicatorsWatch the early-warning signals associated with each risk — rising defect counts, slipping task completion, staff turnover, supplier delays. Indicators let you act before the risk materialises.
  2. Monitor risk probability and impactRe-assess both figures as the project progresses. A risk that was medium-probability at kick-off may be near-certain by integration, and its exposure must be recalculated.
  3. Check whether mitigation actions are effectiveA mitigation that was agreed but never executed, or executed without effect, is worse than none, because the team believes itself protected.
  4. Identify new risksNew risks emerge continuously — from design decisions, from change requests, from the external environment. Every review adds to the register.
  5. Implement contingency plansWhen a risk actually occurs, invoke the pre-agreed contingency. The value of having written it in advance is that the decision is made calmly rather than under pressure.
  6. Update the risk registerRecord status changes, close risks that can no longer occur, add new entries, and revise exposure values after every review.
  7. Communicate risk status to stakeholdersReport the top risks, their trend and the actions in progress. Stakeholders who are surprised by a risk that was in the register for months lose confidence in the whole plan.

7.2 The risk register

Risk register

A document used to record and monitor risks. A full register holds, for each risk: an identifier, a description, the category, probability, impact, risk exposure, the chosen response strategy, the planned actions, the owner, the current status, and the review date.

8PERT — Program Evaluation and Review Technique

Scheduling when you do not know how long anything will take

8.1 What it is

PERT stands for Program Evaluation and Review Technique. It is a network-based project management technique used for planning, scheduling, monitoring and controlling a project. It was developed in 1958 for the US Navy's Polaris missile programme, where nothing being built had ever been built before — which is exactly the situation PERT is designed for.

Its distinguishing feature is that it treats activity durations as uncertain. Where CPM asks "how long does this take?", PERT asks "how long does this take at best, at worst, and most likely?" and works with the distribution.

8.2 Objectives

  • Estimate the expected time required to complete the project.
  • Identify the activities that are critical to project completion.
  • Determine the probability of completing the project within a specified time.
  • Identify the activities where delays will affect the overall project, so that monitoring effort can be concentrated there.

8.3 Characteristics

Six defining characteristics of PERT
#CharacteristicMeaning
1Probabilistic techniqueActivity durations are uncertain and are modelled with three estimates rather than one fixed figure.
2Network basedThe project is represented as a network of activities and events showing sequence and dependency.
3Event orientedThe original formulation focuses on events and milestones — points in time — rather than on the activities between them.
4Time focusedConcerned primarily with completion time; the original method had no cost dimension.
5Suited to uncertain projectsAppropriate for research and development, new product development and one-off projects with no historical duration data.

8.4 The three time estimates

The three estimates collected for every activity
SymbolNameDefinition
t₀Optimistic timeThe minimum possible time the activity could take if everything goes better than expected. Roughly a 1% chance of being beaten.
tₘMost likely timeThe normal completion time — the duration that would occur most often if the activity were repeated many times. The mode of the distribution.
tₚPessimistic timeThe maximum expected time if significant things go wrong. Excludes catastrophes such as fire or strike.
Expected time   tₑ = (t₀ + 4tₘ + tₚ) / 6

Variance of an activity   σ² = ((tₚ − t₀) / 6)²

Standard deviation   σ = (tₚ − t₀) / 6
Where the formulas come from

PERT assumes each activity duration follows a Beta distribution, which is bounded at both ends and can be skewed — a realistic shape, since an activity can finish only a little early but can run very late.

The weighted mean (t₀ + 4tₘ + tₚ)/6 is the Beta distribution's approximate mean, giving the most likely value four times the weight of the two extremes combined.

The variance formula comes from the assumption that the full range t₀ to tₚ spans about six standard deviations, so σ = (tₚ − t₀)/6 and σ² is its square. If you are asked why the divisor is 6, that is the answer.

8.5 The network and the critical path

A PERT network shows activities and their sequence and dependency relationships from a Start node to a Finish node.

Critical path

The longest path through the network, measured in total expected duration. It determines the minimum possible project duration. Every activity on it has zero float, meaning any delay to any critical activity delays the whole project by the same amount.

Note the counter-intuitive point that is regularly examined: the critical path is the longest path, not the shortest. It is "critical" because it has no slack, not because it is fastest.

Float and the forward and backward pass

The four dates computed for every activity
TermFull nameHow it is found
ESEarliest StartForward pass: the largest EF of all immediate predecessors
EFEarliest FinishEF = ES + tₑ
LFLatest FinishBackward pass: the smallest LS of all immediate successors
LSLatest StartLS = LF − tₑ
Total float = LS − ES = LF − EF
An activity is critical when its total float is zero. Free float is the delay possible without affecting the earliest start of any following activity.

8.6 The seven steps

  1. Identify the activities and their dependenciesList every activity needed to complete the project and record which activities must precede which.
  2. Estimate the three times for each activityCollect t₀, tₘ and tₚ from the people who will do the work, not from the schedule you want.
  3. Calculate the expected timetₑ = (t₀ + 4tₘ + tₚ) / 6 for every activity.
  4. Calculate the varianceσ² = ((tₚ − t₀) / 6)² for every activity.
  5. Construct the networkDraw the activity-on-node or activity-on-arrow diagram from Start to Finish, honouring the dependencies.
  6. Determine the critical pathCalculate the total duration of every path through the network and identify the longest. Alternatively run the forward and backward pass and pick the activities with zero float.
  7. Estimate the probability of completionSum tₑ along the critical path to get the expected project duration, sum the variances along it, and use the normal distribution to find the probability of meeting a target date.
Expected project duration   Tₑ = Σ tₑ  (along the critical path)

Project variance   σ²ₚ = Σ σᵢ²  (of critical path activities only)

Project standard deviation   σₚ = √( Σ σᵢ² )

Z = (Tₛ − Tₑ) / σₚ  where Tₛ is the scheduled or target date. Look Z up in a standard normal table for the probability.
Two things students get wrong here

First, variances add, standard deviations do not. You must sum the σ² values and take the square root at the end. Adding the σ values directly is a guaranteed lost mark.

Second, sum the variances only for activities on the critical path, not for every activity in the network.

Worked EVM example

At the status date, a project has BAC = ₹10,00,000, PV = ₹4,00,000, EV = ₹3,50,000 and AC = ₹4,20,000.

CV = 3,50,000 − 4,20,000 = −₹70,000; the completed work cost more than its budgeted value.

SV = 3,50,000 − 4,00,000 = −₹50,000; less work is complete than planned.

CPI = 3,50,000 ÷ 4,20,000 = 0.833; SPI = 3,50,000 ÷ 4,00,000 = 0.875.

Assuming current cost efficiency continues, EAC ≈ BAC ÷ CPI = 10,00,000 ÷ 0.833 = ₹12,00,000. Therefore VAC = 10,00,000 − 12,00,000 = −₹2,00,000, and ETC = 12,00,000 − 4,20,000 = ₹7,80,000.

TCPI to finish within the original BAC = (10,00,000 − 3,50,000) ÷ (10,00,000 − 4,20,000) = 6,50,000 ÷ 5,80,000 = 1.12. The remaining work must be delivered at 1.12 cost efficiency to recover the original budget.

The most important distinction

EV is the budgeted value of work completed, not the amount spent. AC tells you what the work cost; EV tells you what the completed work was worth according to the approved budget. That separation is what lets EVM detect both overspending and under-delivery.

9.6 Prioritizing monitoring

Definition

Prioritizing monitoring is the process of identifying the most important project activities, deliverables, risks and performance areas that require continuous and closer monitoring, so that limited management attention is spent where it changes the outcome.

The premise is economic. Collecting and checking progress data costs time and money, and it also costs goodwill — a team monitored on everything equally feels distrusted and starts reporting defensively. So monitoring effort is rationed and directed at the items where early detection matters most.

9.7 Why it is done

  • Identify deviations at the earliest stage, while correction is still cheap.
  • Focus management attention on critical items instead of spreading it thinly.
  • Control project cost and schedule by catching overruns before they compound.
  • Reduce the impact of risk, because closely watched risks are caught near their trigger point.
  • Ensure deliverables are completed on time, protecting downstream dependencies.
  • Enable timely corrective action, which is the whole purpose of monitoring.

9.8 Areas that are monitored

Critical activities · high-risk activities · cost · schedule · quality · resources · milestones · changes.

9.9 Factors used to set priority

What makes an activity worth watching closely

The standard monitoring priority order

If asked to rank activities for monitoring, the conventional order is: (1) critical path activities, (2) activities with no free float, (3) activities with less than a specified float, such as under one week, (4) high-risk activities, (5) activities using scarce or critical resources.

10Getting the Project Back to Target

What to do once monitoring says you have drifted

Definition

The process of taking corrective action when actual performance deviates from the planned performance, so that the project returns to its agreed targets for time, cost, scope and quality.

10.2 The project control cycle

Plan→Monitor→Compare→Identify deviation→Take corrective action→Re-monitor

The cycle is closed, not linear. Corrective action feeds back into monitoring, and if the action fails to close the gap the cycle repeats with a stronger intervention.

10.3 The six steps

  1. Identify the deviationCompare actual progress, cost and quality against the baseline. Quantify the gap — "four days late on activity D", not "running a bit behind".
  2. Determine the causeEstablish the root cause rather than the symptom. Late delivery caused by an absent developer needs a different fix from late delivery caused by an underestimate.
  3. Assess the impactWork out what the deviation does to the critical path, the final date, the budget and the dependent activities. A slip on an activity with six weeks of float may need no action at all.
  4. Develop corrective actionsGenerate options and evaluate their cost, feasibility and side-effects. Every option that recovers time costs either money or scope.
  5. Implement the chosen actionExecute it, communicate the change to everyone affected, and get approval where the action alters the baseline.
  6. Monitor the resultVerify that the action actually closed the gap. If it did not, return to step 1 with revised information.

10.4 Possible corrective actions

  1. Identify the activities causing the delayConcentrate on critical path activities; recovering time on a non-critical activity changes nothing.
  2. Assign additional developers to critical activitiesEffective only for work that genuinely divides, and only early. See the warning below.
  3. Prioritise critical tasksRedirect the best people and the scarce resources onto the critical path and let non-critical work absorb its float.
  4. Reduce avoidable waiting timeRemove idle handover gaps, waiting for approvals, waiting for environments. This recovers time at almost no cost and is always the first thing to try.
  5. Review resource allocationRebalance across the network, moving people off activities with float onto activities without.
  6. Update the schedule after approvalIf the gap cannot be recovered, re-baseline formally with stakeholder sign-off rather than quietly working to a date everyone knows is false.

10.5 The two structural strategies

The textbook framing — you are always doing one of these two things
StrategyWhat it meansCost
Shorten the critical pathAdd resources, work overtime, use better tools, buy rather than build a component, increase parallelism within an activityUsually money, and sometimes quality if testing is compressed
Reconsider the precedence requirementsOverlap activities that were planned in sequence — "fast-tracking" — for example starting coding on a stable module before the whole design is signed off, or delivering in incrementsUsually risk, because you commit to work that a later decision may invalidate
Brooks's Law — quote it and you gain a mark

"Adding manpower to a late software project makes it later." New staff must be trained, they consume the time of existing staff, and communication paths grow as n(n−1)/2. Adding people helps only if the work is genuinely divisible and there is enough time left for the newcomers to become productive. An answer that recommends adding developers without this caveat is an incomplete answer.

When neither strategy closes the gap, the remaining options are negotiated rather than technical: reduce the scope by deferring lower-priority features to a later release, relax a quality target with explicit stakeholder agreement, or renegotiate the deadline. All three require formal approval, which is where change control takes over.

11Change Control

Making sure changes happen deliberately rather than by accident

Definition

Change control is the systematic process used to identify, evaluate, approve, implement and monitor changes to an approved project plan or baseline.

A baseline is a formally reviewed and agreed version of a deliverable — a requirements specification, a design document, a schedule, a budget — that thereafter can only be altered through this process.

11.1 What kinds of things change

Changes may involve project scope, requirements, schedule, cost, resources, technology, design, quality standards or deliverables. In practice a change to any one of these propagates to the others, which is precisely why impact analysis is a mandatory step.

11.2 The process

Change request→Record the change→Impact analysis→Review→Approve or reject→Implement→Verify→Update baseline
  1. Change requestA user, developer or stakeholder perceives a need and raises a formal request describing what should change and why.
  2. Record the changeThe request is logged in a change register with a unique identifier, originator, date and description. Nothing is evaluated until it is written down, which alone stops most informal scope creep.
  3. Impact analysisTechnical staff assess what the change would cost in effort, money and time, what it affects — other requirements, design, test cases, documentation — and what new risks it introduces.
  4. ReviewA change control board or equivalent authority, containing both user and development representatives, considers the request against its cost and its benefit.
  5. Approve or rejectA decision is made and recorded with its reasoning. Rejected requests stay in the register so the same idea is not re-argued from scratch later.
  6. ImplementApproved changes are scheduled into the work plan, resourced, and carried out. The change is not "squeezed in"; it is planned.
  7. VerifyThe implemented change is tested and reviewed to confirm it does what was approved and has not broken anything else.
  8. Update the baselineThe specification, design, schedule, budget and documentation are all updated, and the new version becomes the baseline for future work.

11.3 Types of change

Scope changes · schedule changes · cost changes · resource changes · technical changes. A single request often falls into several types at once — adding a feature is a scope change that causes a schedule change and a cost change.

Theory questions

Distinguish between an External Output and an External Inquiry, with an example of each.

Both send data across the application boundary to the user. The difference is processing logic.

An External Output applies additional processing — it calculates, derives, totals, or updates an internal file on the way out. Example: a monthly sales report that computes regional totals and a year-to-date figure.

An External Inquiry performs pure retrieval — data is fetched and displayed exactly as stored, with no derivation and no file update. Example: entering a customer ID and seeing that customer's stored name and address.

The weights differ accordingly: EO is 4/5/7 while EQ is 3/4/6, reflecting the extra work in the output case.

Why is the VAF bounded between 0.65 and 1.35?

VAF = 0.65 + 0.01 × DI, and DI is the sum of 14 characteristics each rated 0 to 5.

Minimum DI = 14 × 0 = 0, giving VAF = 0.65 + 0 = 0.65.
Maximum DI = 14 × 5 = 70, giving VAF = 0.65 + 0.70 = 1.35.

The design intent is that the technical environment may adjust the measured functional size by at most ±35%. The bound keeps function points a size measure driven by functionality, rather than letting subjective environmental judgement dominate the count.

Explain the four risk response strategies with a software example for each.

Avoidance — change the plan so the risk cannot occur. Example: an unproven new framework is dropped in favour of a mature, well-tested one.

Reduction (mitigation) — act to lower the probability or the impact. Example: train the team on the required technology to reduce defects caused by inexperience.

Transfer — move responsibility to another party, usually for a fee. Example: use a managed cloud service with an SLA instead of running your own server, so availability becomes the provider's obligation.

Acceptance — record the risk and take no preventive action, because the impact is small or control costs more than the exposure. Example: accept a minor delay in a non-critical documentation task.

Why is the critical path the longest path rather than the shortest?

The project cannot finish until every activity is complete, so its minimum duration equals the duration of the longest chain of dependent activities. Any shorter path finishes with time to spare — that spare time is its float.

"Critical" therefore means "has no float", not "fastest". Every activity on the longest path has zero float, so a one-day delay on any of them delays the entire project by one day. That is why monitoring effort is concentrated there.

Compare hazard assessment with risk control.

Hazard assessment is analytical and predictive. It asks what could go wrong, how likely it is and how severe it would be. It happens mainly during planning and at review points, and its output is the risk register with prioritised exposure values. Its techniques are checklists, brainstorming and the probability–impact matrix.

Risk control is operational and continuous. It asks whether things are going wrong now and what to do about it. It runs throughout execution, and its output is corrective action, invoked contingency plans and an updated register. Its techniques are indicator tracking, progress comparison and reviews.

In short: assessment decides what to worry about; control is the weekly work of doing something about it. The full seven-dimension comparison is in §7.4.

A project is four weeks behind schedule. The manager proposes adding six developers. Evaluate this.

The proposal may make the situation worse, by Brooks's Law: adding manpower to a late software project makes it later. New staff need training, they consume the time of the existing productive staff, and communication paths grow as n(n−1)/2.

It can help only when three conditions hold: the remaining work is genuinely divisible, enough time remains for newcomers to become productive, and the added people are placed on critical path activities — adding staff to work that already has float changes nothing.

Better first options, in order of cost: remove avoidable waiting time and approval delays; reallocate existing staff from activities with float onto the critical path; fast-track by overlapping activities whose precedence is a convention rather than a technical necessity. If the gap still will not close, the honest responses are to reduce scope, relax a quality target, or renegotiate the deadline — each through formal change control.

Why does an organisation need change control? Give four consequences of not having it.

Change control ensures that every alteration to an approved baseline is identified, costed, evaluated, authorised and traceable, so that the plan continues to describe the work actually being done.

Without it: (1) uncontrolled scope growth, as features accumulate informally; (2) budget overrun, because unbudgeted work consumes contingency then budget; (3) schedule delay, since work is added without adding time; (4) unauthorised changes and team confusion, as different people work to different versions of the requirement. Tracking becomes impossible because there is no stable baseline to measure against, and project risk rises because nobody assessed the impact of what was added.

State the COCOMO II sub-models and say when each is used.

Application Composition — used for prototyping and rapid application development where systems are assembled from screens, reports and existing components. Size unit: object points.

Early Design — used after requirements are settled but before the architecture is fixed. Size unit: function points converted to KLOC, with 7 cost drivers.

Post-Architecture — used once the architecture is defined and development is underway. Size unit: KLOC, with 17 cost drivers and 5 scale factors.

The progression reflects increasing knowledge: as you learn more about the system, you can afford a model with more parameters.

Explain expert judgment and estimation by analogy. How can a project manager reduce the weaknesses of each?

Expert judgment uses relevant people’s experience to predict effort, duration or cost. Reduce bias by defining scope first, collecting independent estimates, using a Delphi-style review, recording assumptions and comparing the estimate with actual results.

Analogy scales measured results from a genuinely similar completed project. Reduce false similarity by comparing size, technology, domain, team, reuse, integration and quality conditions, then applying explicit adjustments and cross-checking with another method.

What should a project monitoring framework define?

It should define the baseline, indicators, units and calculation rules, data sources, owners, status date, collection frequency, green/amber/red thresholds, reporting audience, escalation route and action-closure process. The purpose is to turn measurement into a decision and a response.

Why is EV not the same as AC, and what do CPI and SPI tell the manager?

EV is the budgeted value of the work actually completed; AC is the actual money spent on that work. CPI = EV/AC measures cost efficiency, so below 1 means the work costs more than its budgeted value. SPI = EV/PV measures schedule efficiency, so below 1 means less work is complete than planned by the status date.

Compare fixed-price, cost-reimbursable and time-and-materials contracts.

Fixed-price gives one agreed price for a defined scope and places more cost risk on the supplier. Cost-reimbursable pays allowable cost plus a fee and leaves more cost risk with the buyer, so it suits uncertain or exploratory work. Time-and-materials pays agreed rates for actual time and materials; it is flexible but needs a cap, timesheet controls and output expectations.

Describe contract acceptance and explain why delivery alone is not acceptance.

Acceptance is the authorised buyer’s formal confirmation that the submitted deliverable meets the contract’s measurable criteria. The buyer inspects or tests it, records defects, requests correction and retest where needed, and signs an acceptance certificate or written rejection. Delivery alone proves only that something was submitted; acceptance may trigger payment, warranty or handover, so the criteria and decision must be explicit.
